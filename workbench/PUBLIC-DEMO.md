# Governance Explorer — static public demo

This is a build mode of the existing React workbench, not another frontend or a
JavaScript governance engine. The local application keeps its import, Python
analysis, policy/review, read-only plan inspection and report features.

## Generate and verify evidence

From the repository root, with the project installed in a Python 3.12+ environment:

```powershell
.\.venv-workbench\Scripts\python.exe sample/public-demo/generate.py
.\.venv-workbench\Scripts\python.exe sample/public-demo/generate.py --check
```

Generation uses load_dbt_graph, analyze_downstream_impact, build_impact_result,
verify_impact_result_integrity and the existing HTML renderer. It requires no web
server, PostgreSQL, commercial tenant, credentials or provider discovery.
`--check` verifies every generated byte and rejects unexpected files without writing.
The `--output` argument can select an independent artifact directory.

Each scenario distributes graph.json, result.json (governance-impact-result v1),
workspace.json (private view projection) and report.html. scenarios/manifest.json
records identifiers, descriptions, contract/version, result content identity and
SHA-256 of every scenario file. The frontend metadata is an identical generated
copy. No timestamps or absolute developer paths are included. SHA-256 verifies
integrity, not truth of the metadata or identity of its author.

- **Orders impact:** orders → order_totals → revenue_report; inventory not reached.
- **Isolated inventory:** changing inventory identifies no consumers in the supplied
  graph. Clear is not a complete-coverage, zero-risk or production-safety guarantee.
- **Multi-branch data pipeline:** order_events feeds clean_orders and risk_flags;
  clean_orders feeds daily_revenue/monthly_metrics, risk_flags feeds risk_summary.
  reference_calendar is disconnected in the supplied dependency evidence. These
  models are synthetic and do not imply Snowflake, Databricks, Power BI or Collibra
  integration.

## Build both experiences

```powershell
npm --prefix workbench run build:public
npm --prefix workbench run build
```

`build:public` writes `workbench/dist-public/`. Uploading these files to a normal
HTTPS static host is sufficient in principle; no deployment is performed here.
It does not include FastAPI, Python or Node server code. `build` independently
regenerates the packaged local workbench frontend. Neither build overwrites the
other. No package version or publication workflow is changed.

For local transport-only preview, optionally copy dist-public into an independent
folder and run:

```powershell
node workbench/scripts/serve-public.mjs "C:\path\to\static-copy" 8787
```

Open http://127.0.0.1:8787. The helper serves files only, binds to loopback, rejects
non-GET/HEAD requests, and implements no API or analysis. It is not part of the
public build. A visitor requires only a browser. The static host must use HTTPS
(or localhost for preview) for browser SHA-256 verification. Relative URLs support
hosting under a subdirectory; navigation uses URL fragments.

## Boundaries

The public runtime replaces the local runtime at build time. It reads only files
for whitelisted scenario identifiers, verifies SHA-256 before use, and offers only
precomputed report downloads. There is no upload, URL input, live analysis,
policy evaluation, plan execution, mutation endpoint or credential request.
Graph, inspector, paths and relations are shared components. All displayed impact
classifications/distances come from Python artifacts; layout is a view operation.

Only Dashboard, Lineage and Impact Analysis have recorded scenario data and appear
in public navigation. Missing policies are explicitly absent, not compliance.
Changing selection does not run a new analysis; the report always belongs to the
selected scenario, not a hypothetical change on the highlighted node.

The full workbench remains open source. Its GitHub download link is intentionally
not activated until this integration is integrated and published; no release is
invented. Usability measured by automation is not human acceptance. Fresh tabs
provide clean application state; isolated browser profiles and a timed independent
human test require separate verification.

## Focused validation

```powershell
.\.venv-workbench\Scripts\python.exe -m pytest -q tests/test_public_demo.py tests/test_workbench_api.py tests/test_impact_html.py tests/test_report_cli.py tests/test_offline_impact_demo.py
npm --prefix workbench run test
npm --prefix workbench run lint
npm --prefix workbench run build:public
```

Inspect the output inventory, verify the reports against render_impact_report and
check HTTP request logs for absence of /api requests. Test all three scenarios with
FastAPI stopped. Do not expose the local workbench API to publish this static demo.
